# hypr2d design

A Hyprland plugin giving every monitor its own 2D workspace grid, an overview
of all grids at once (with special workspaces) where windows can be dragged
anywhere including across monitors, a finger-tracking 2D trackpad swipe, a
waybar module, and a small extension API. Keep it straightforward and high
quality: small surface, well tested, no feature creep.

## Environment

- Hyprland **0.56** (the user's flake input: `github:hyprwm/Hyprland` at rev
  `e368c13c27a42a173b9e08fa0bf413f9f7073187`). Config is **Lua**
  (`~/.config/hypr/hyprland.lua`, generated by Home Manager with
  `configType = "lua"`); dispatchers use the `hl.dsp.*` form, e.g.
  `hyprctl dispatch 'hl.dsp.focus({ workspace = 23 })'`.
- NixOS + Home Manager. The user's HM repo: `~/Config/home-manager`
  (Hyprland config under `users/wolf/desktop/hyprland/`; current grid script
  `workspace2d.sh`, binds in `keybinds.nix`, gestures in `default.nix`).
- The plugin ABI is not stable: build against the exact Hyprland the user runs.
  The flake takes a `hyprland` input; the user's HM flake will set
  `inputs.hypr2d.inputs.hyprland.follows = "hyprland"`.

## Architecture

```
core/     Rust (lib + staticlib): grid model, numbering, moves, swipe physics,
          overview layout & hit-testing, drag state machine, protocol (serde).
          Pure logic, no Hyprland types, thoroughly unit-tested.
plugin/   C++: thin shim. Plugin entry, dispatcher/hyprctl registration,
          gesture & input hooks, render-pass elements for overview/swipe,
          workspace texture rendering. Calls core through `cxx`.
cli/      Rust: `hypr2d` CLI (state, waybar module, client of the socket).
client/   Rust crate `hypr2d-client` for the extension socket (M6).
nix/      flake parts: package (one .so linking the staticlib), HM module,
          `nix run .#nested` (nested Hyprland with a test config and the
          plugin preloaded), checks.
```

Rules:
- Logic lives in Rust; C++ only translates Hyprland state/events in and
  applies commands/draws out. Every bridge call is wrapped so a Rust panic can
  never unwind into Hyprland (catch_unwind → log + no-op).
- No polling anywhere. No `hyprctl` subprocesses from the plugin.
- Borrow ideas/code (MIT) from hyprexpo (overview rendering) and hyprkool
  (grid logic) with attribution where code is reused.

## Grid model

- **One grid per monitor.** Default 8×8, wrapping on. Configurable per
  monitor: columns, rows, wrap.
- **Numbering must match the user's current scheme** so nothing moves on
  switchover: `workspace = 10 * (y * 8 + x) + monitor_id + 1`
  (`max_screens = 10`, `matrix_size = 8`, x/y zero-based, monitor_id is
  Hyprland's monitor id). Make the formula configurable (stride, columns).
- Moves:
  - `move <dir>`: focused monitor goes to its neighbouring cell.
  - `move <dir> all`: every monitor moves one cell in that direction, each
    from its own current cell; focus returns to the originally focused monitor.
  - `carry <dir>`: move the active window to the neighbouring cell and follow.
  - `goto <x> <y> [monitor]`.
- Animation: horizontal moves slide horizontally, vertical moves slide
  vertically, decided per move by the plugin (today a script rewrites the
  `workspaces` animation style before each move; that hack goes away).
- Special workspaces are not part of the grid but are first-class in the
  overview and drag & drop.

## Binds

All of the user's current binds stay; only their targets change.

| Bind | Today | hypr2d |
|---|---|---|
| SUPER+CONTROL+H/J/K/L | `workspace2d left/down/up/right` | `hypr2d:move left/down/up/right` |
| SUPER+SHIFT+H/J/K/L | `workspace2d move_left/…` | `hypr2d:carry left/…` |
| SUPER+ALT+J | `workspace2d down all && toggle_special("")` | `hypr2d:move down all` then the same `toggle_special("")` |
| SUPER+ALT+K | `workspace2d up all && toggle_special("")` | `hypr2d:move up all` then `toggle_special("")` |
| 3-finger swipe (laptop) | `execGesture` → `workspace2d …` on completion (swipe up = `down`, natural) | tracked 2D swipe (M2), same natural direction |
| new: SUPER+TAB (suggested) | — | `hypr2d:overview` |

The script also runs `pkill -RTMIN+1 waybar` after moves to refresh a waybar
module; the hypr2d waybar module streams instead, so that goes away.

## Tracked swipe (M2)

Begin: accumulate 2D travel and select one of eight sectors after axis-lock
distance. Use 50 ms exponential displacement/velocity estimates, diagonal sectors
±15° (cardinals ±30°), and 8° plus sustained-distance hysteresis for re-targeting.
Track at 1:1 with up to four workspace offsets (current, horizontal, vertical,
diagonal); pure cardinal motion uses two. Resist blocked axes independently.
Release: project velocity with constant deceleration, normalize by viewport width
and height, and choose the nearest origin/eight-neighbour target. Each diagonal
axis must independently exceed midpoint and minimum distance; clamped axes degrade
to valid cardinal motion. Settle with a critically damped 2D spring starting at
release velocity. Rust owns all decisions, geometry and physics; C++ applies the
workspace list and offsets. See README for tunables and physical hand-tests.

## Overview (M4/M5)

- Shows **all monitors' grids simultaneously**, one panel per monitor, panels
  arranged like the physical monitor layout, each panel the monitor's full
  grid with live workspace thumbnails; plus a strip of special workspaces
  (named via config or by their main app; empty ones dimmed/hidden; ones
  currently shown highlighted).
- Keyboard: hjkl/arrows within a grid, Tab/Shift-Tab across monitors and the
  specials strip, Enter to go, Esc to close. Mouse: click to go.
- Drag & drop: drag a window thumbnail to any cell of any monitor's grid, into
  or out of a special workspace, onto another window to swap, or (floating)
  to a precise spot. Ghost + target highlight, Esc cancels.
- Rendering follows hyprexpo's approach (render workspaces to framebuffers on
  open, then compose); include special workspaces, which hyprexpo skips.
  Layout and hit-testing math live in Rust.

## Waybar (M3)

`hypr2d waybar [--monitor NAME]` is a waybar `custom` module with
`"return-type": "json"` that prints one JSON line per change (subscribe to
socket2 / the extension socket; never poll). Text: a compact minimap around
the current cell (configurable radius, e.g. 3×3) using glyphs for current /
occupied / empty / urgent; classes for styling; tooltip listing each occupied
cell's windows; on-click / on-scroll call the CLI to move. Must look good
with the user's OneDark Extra Dark bar (black background).

## Extension API (M6)

Three layers, no agent-specific code in this repo:
1. Dispatchers / `hyprctl hypr2d …` for binds and scripts.
2. socket2 events: `hypr2d>>cell>>MONITOR,X,Y`, `hypr2d>>overview>>open|close`,
   `hypr2d>>drop>>…`.
3. `$XDG_RUNTIME_DIR/hypr/$HYPRLAND_INSTANCE_SIGNATURE/hypr2d.sock`: versioned
   JSON lines. Annotations (label, badge, dot, colour, tooltip) on cells,
   specials, windows; reserved regions (e.g. "row 7 = agents", titled band in
   the overview, optionally skipped by moves); placement ("window W to cell");
   subscriptions to activate/drop on owned regions. Everything a client sets is
   dropped when its connection closes. Schema documented and versioned;
   `hypr2d-client` crate wraps it.

## Testing

- `cargo test` for core (the bulk of coverage).
- `nix run .#nested`: nested Hyprland (same build the plugin targets) with a
  test config and the plugin preloaded; reload via `hyprctl -i N plugin
  unload/load`. Never load an untested build into the user's live session.
- CI (GitHub Actions + `nix flake check`): build against the pinned Hyprland,
  core tests, clippy `-D warnings`, rustfmt, clang-format, and a headless or
  nested integration test that drives dispatchers via hyprctl and asserts the
  resulting workspace ids. Also a non-blocking job against Hyprland main to
  catch ABI breaks early.

### API inspection (exact pinned revision)

Inspected Hyprland `e368c13c27a42a173b9e08fa0bf413f9f7073187`, not
headers from the system profile. These are source findings; only the bridge
and plugin lifecycle are exercised by the M0 runtime smoke test.

- **Dispatchers / IPC (M1, corrected after implementation inspection):**
  `addDispatcherV2` is declared in the header but its implementation returns
  false unconditionally (`src/plugins/PluginAPI.cpp:202`). Lua `dispatch`
  evaluates `hl.dispatch(expression)` rather than parsing legacy dispatcher
  strings. Commands therefore use `addLuaFunction` dispatcher constructors
  (`hl.plugin.hypr2d.move("left")`, etc.) and a custom `hypr2d` IPC command.
  The old literal `hypr2d:move left` form is unavailable on this revision. `registerHyprCtlCommand` accepts an
  `IPC::Socket1::SCommand` for `hyprctl hypr2d ...`; its callback receives the
  output format. Lua also has `addLuaFunction` for plugin namespaces.
  Sources: `src/plugins/PluginAPI.hpp`, `src/ipc/s1/S1.hpp`.
- **socket2 (M1):** `IPC::Socket2::sock()->postEvent(SEvent{event, data})`
  queues compositor IPC events. The wire format is `event>>data` plus a newline;
  use event `hypr2d` and data `cell>>MONITOR,X,Y`, etc. This is an internal
  compositor API, not a `HyprlandAPI` wrapper. No subprocess is needed.
  Sources: `src/ipc/s2/S2.hpp`, `src/ipc/s2/S2.cpp`.
- **Animation (M1):** `Animation::Workspace::startAnimation` takes an optional
  style per call, including vertical slide styles. `CHLWorkspace` exposes
  `m_renderOffset`, `m_alpha`, `m_forceRendering`, and `m_animationStyle`.
  No config rewrite is required. The actual monitor workspace transition
  must be coordinated with these overrides and tested for overlapping moves.
  Sources: `src/animation/WorkspaceAnimationController.{hpp,cpp}`,
  `src/output/Monitor.cpp`, `src/workspace/HLWorkspace.hpp`.
- **Swipe input (M2):** retain RAII listeners from
  `Event::bus()->m_events.gesture.swipe.{begin,update,end}.listen(...)`.
  All three are cancellable. `CInputManager::onSwipe*` checks
  `SCallbackInfo::cancelled` before built-in gesture handling and forwarding
  to clients. Begin includes finger count; updates include delta/time; end
  includes cancellation. Cancel the whole claimed sequence, and leave other
  gestures alone. `CTrackpadGestures::addGesture` / `ITrackpadGesture` are
  another internal route, but cancellable event listeners avoid taking over
  global gesture registrations. Sources: `src/event/EventBus.hpp`,
  `src/managers/input/InputManager.cpp:2340`, `src/devices/IPointer.hpp`.
- **Tracked rendering (M2):** `CUnifiedWorkspaceSwipeGesture` already drives
  neighbour workspaces using `m_renderOffset->setValueAndWarp`, forces
  rendering and damages the monitor. It is useful mechanism reference, but
  its neighbour selection and thresholds are not the Rust grid policy.
  Sources: `src/managers/input/UnifiedWorkspaceSwipeGesture.cpp`.
- **Textures / overview (M4):** `Render::IHyprRenderer` exposes
  `beginFullFakeRender` and `endRender`, with protected workspace-drawing
  methods (see the M4 prototype findings below); framebuffers expose textures.
  There is no high-level "snapshot workspace" plugin function. This is
  internal renderer integration with GL context, damage, workspace visibility,
  active workspace and feedback state to preserve and restore.
  Sources: `src/render/Renderer.hpp`, `src/render/Framebuffer.hpp`.
- **Render passes (M4):** custom `IPassElement` implementations can be added
  with `g_pHyprRenderer->m_renderPass.add(...)`; render-stage events are
  available. `draw()` now returns additional pass elements; blur requirements,
  pass name and type are pure virtual, with bounding/damage/opaque hooks.
  Built-in texture pass elements may reduce custom drawing work. Pass elements
  and input/event listeners must not outlive plugin unload.
  Sources: `src/render/pass/{Pass,PassElement,TexPassElement}.hpp`,
  `src/event/EventBus.hpp`.

### hyprexpo reference and remaining risks

The upstream hyprland-plugins repository removed hyprexpo as unmaintained in
commit `3aa21f2e0ca72412f1b434c3126f8f1fec3c716c`. Inspected its last version,
[`b6e080577daf6575b95e6733dd2e2aef714bcf10/hyprexpo/overview.cpp`](https://github.com/hyprwm/hyprland-plugins/blob/b6e080577daf6575b95e6733dd2e2aef714bcf10/hyprexpo/overview.cpp).
It creates per-cell framebuffers, uses full-fake renders, temporarily switches
active/visible workspace state, and composes via a custom pass element.
It suppresses the special workspace while capturing ordinary cells except the
starting workspace. This does not directly implement the required special strip.
It also refers to older workspace and animation APIs (e.g. `CWorkspace` and
`g_pDesktopAnimationManager`), so it must be adapted, not copied verbatim.
No upstream code is copied into the M0 plugin.

- **M1:** no identified API blocker. Need integration tests for per-monitor
  transitions, per-call slide direction, numbering, Lua dispatcher invocation,
  IPC formatting and unload cleanup before claiming implementation support.
- **M2:** no identified input API blocker. Actual physical trackpad behaviour,
  cancellation, neighbour visibility, reversals and offset cleanup remain
  untested. The nested Wayland window must receive gestures from its parent;
  synthetic input alone will not establish physical feel.
- **M4:** internal APIs allow the approach, but compatibility is not runtime
  proven. Special-workspace capture, all-monitor composition, renderer backend
  support, damage-driven live refresh, state restoration and GPU memory at
  8×8 per monitor need a separate rendering prototype within M4. Full-resolution
  textures for all cells are expensive; size captures to displayed thumbnails.
  This is the main implementation risk, not a confirmed impossibility.

### M1 implementation

Rust owns grid validation, reversible numbering, command parsing, per-monitor
configuration, and plans for moves/carry/all/goto. C++ translates snapshots,
applies compositor actions, and starts animations with per-call grid direction
(including wrap). No animation configuration is rewritten. Shared stride is
global; columns/rows/wrap are per output. See README §Binds for exact Lua calls.
Dispatcher closures are Lua-only and look up the registered callback each time,
so binds cannot retain dangling C++ function pointers after plugin unload.

`hyprctl hypr2d state -j` returns versioned JSON including every grid cell and
its window metadata. `hypr2d>>cell>>MONITOR,X,Y` events follow plugin moves;
`hypr2d>>changed` signals other workspace activations and `hypr2d>>config`
signals runtime grid changes.

Nested integration passed: exact numbering and wrap, Lua dispatch, socket2,
vertical/horizontal render offsets, 57 overlapping move requests, a second
headless output with independent starting cells and preserved focus, no-wrap
edges, and carrying a mapped Foot client. No physical input was injected.
CI uses a NixOS VM with a virtual GPU and a plugin-free Hyprland parent: this Aquamarine build
requires DMA-BUF/DRM support, and a pure pixman/software parent cannot provide
it. The test runs only the isolated nested plugin instance.

The nested launcher requires `WAYLAND_DISPLAY` and sets
`LIBSEAT_BACKEND=none`: the deprecated-looking `AQ_BACKEND=wayland` variable
is not implemented by this Aquamarine revision. Disabling seat access prevents
nested DRM/input-device acquisition. The disposable CI VM uses root for its
virtual GPU's authenticated dumb-buffer allocations; user-session integration
is tested separately as the normal unprivileged user.

M1 CI VM validation passed as well as the unprivileged nested run. The
non-accelerated virtio GPU exposes a render node that cannot allocate dumb
buffers; the test aliases that node to its authenticated primary node **inside
the disposable VM only**. This keeps the exact compositor and plugin ABI while
allowing software rendering of the nested window. The VM shuts down after the
suite. Configured Lua binds and a configuration guard are also exercised.

### M2 implementation

`core/src/swipe.rs` owns axis locking, finger-distance tracking, natural
inversion, velocity smoothing/decay, threshold decisions, bounded edge
resistance and critically damped release motion. The bridge returns offsets,
workspace targets and the settlement deadline; C++ only applies them.
The gesture's logical cell commits on release, so a second gesture during
settling starts from the already committed cell. Keyboard moves and external
workspace transitions interrupt tracking. Specials and other finger counts are
left to native handling.

The shim retains cancellable swipe listeners and a render callback. While
settling it explicitly schedules the next frame (adding already-full damage
alone does not schedule one in 0.56). A one-shot Rust-defined deadline finishes
the spring if output frame callbacks pause. It is cancelled on completion,
interruption, monitor removal or unload; there is no polling or permanent timer.
Monitor removal uses `preRemoved`, before output teardown. The tests also caught
and fixed goto-to-an-already-active-cell failing to focus the selected monitor.

Five physics tests complement the M1 tests. The nested synthetic path emits the
same EventBus events consumed by production listeners and asserts cancellation,
actual compositor render offsets, axis reversal, natural up-to-down movement,
commit/bounce, no-wrap resistance, key interruption, unload/reload during
tracking and removal of the gesture's monitor. This is synthetic coverage;
physical trackpad feel and parent input forwarding are not established by it.
The exact pending hand-test checklist is in README §Tracked swipe.

M2 passed nine Rust tests, formatting/Clippy, and the complete normal nested
suite, including the monitor-removal and paused-frame settlement regressions.
Real trackpad testing remains explicitly pending.

### M3 implementation and final validation

The Rust `hypr2d` CLI uses Unix IPC directly, with explicit instance selection
for tests. `waybar` subscribes to socket2 before its initial snapshot, blocks
on events, fetches state only for relevant changes, and deduplicates rendered
records. No process polling, interval, signal refresh, or hyprctl subprocess is
used. Plugin `ready`/`unloaded` events let the same stream survive plugin reload;
transient IPC errors can recover on the next relevant event. Selected-monitor
moves are planned atomically in the core instead of a client read/goto race.

The minimap is radius-configurable and shows current, occupied, empty and urgent
cells, with escaped window metadata in the tooltip. Waybar's CSS classes apply
to the entire custom widget, so classes describe states present in the minimap;
per-cell colors use Pango spans. This API limit and the exact JSON/CSS examples
are documented in README §Waybar. Click and scroll actions invoke the CLI.

Final x86_64-linux validation passed:

- Fifteen Rust tests (nine core/physics and six CLI/render/stream), rustfmt,
  Clippy with `-D warnings`, C++ formatting and the pinned plugin/CLI build.
- The complete M1–M3 suite in a normal unprivileged nested window and in the
  disposable CI VM, including rapid moves, two-monitor all/focus/carry,
  synthetic swipe offsets/cancellation/settlement/removal/unload, socket events,
  CLI actions, idle deduplication, title/close events and escaping, and stream
  recovery across plugin unload/reload.
- The actual shipped Waybar config and CSS parsed and rendered in the nested
  instance. A nested-only screenshot was visually inspected: compact 3×3
  minimap with OneDark colors on the black bar.
- `nix flake check --builders '' -L` completed successfully. aarch64-linux
  remains untested; physical trackpad checks remain pending per README.

M1–M3 are implemented. M4 and later milestones remain untouched. No live-session
plugin load, Home Manager write, remote creation or push was performed.

### M4 rendering prototype (approval gate; full UI is not implemented)

The pinned GL renderer can capture ordinary **and special** workspaces into
thumbnail-sized framebuffers and compose both monitors' grids in one custom
`IPassElement`. Rust plans the contact sheet and computes the memory/timing
report; C++ performs renderer calls. The test-only `probe` command is enabled
only with `HYPR2D_TESTING=1`; it is not the production overview dispatcher.
The contact sheet is deliberately a rendering fixture, without navigation,
hit-testing, physical-layout policy, input grabs or live refresh.

API details established by the prototype:

- The public entry point is `beginFullFakeRender`, which wraps the protected
  `beginRender(..., RENDER_MODE_FULL_FAKE, ..., simple=true)`. Workspace drawing
  itself is protected. The shim exposes base member pointers through a derived
  access class; it never casts the actual renderer to that class, patches a
  function, or changes access with preprocessor macros. This remains an internal
  API tied to the exact pinned ABI. Only the GL backend was exercised.
- Allocate at thumbnail dimensions, set the framebuffer's image description to
  `monitor->workBufferImageDescription()`, and supply **source-monitor-sized
  damage** while scaling workspace geometry to the thumbnail. Supplying
  thumbnail-sized damage incorrectly clips surfaces because surface damage is
  intersected before render modifiers are applied. Omitting the color description
  crashes 0.56's shadow renderer; the corrected path renders decorations too.
- Ordinary captures suppress all specials, including special dim/blur. Special
  captures use the workspace-window pass directly, with a plain background;
  otherwise the full workspace path draws specials again in its global specials
  loop. Both hidden specials and an already-shown special are covered.
- Capture only between frames. Save and restore the render data/projection,
  render mode, pass queue, feedback/snapshot flags, framebuffer bindings and
  viewport, monitor active normal/special pointers, damage ring/history,
  pending buffer references and blur scheduling flag. Temporarily override
  workspace alpha/offset **values**, never animation goals, beginnings, timing,
  callbacks or registrations. Visibility stays untouched; force-rendering is
  scoped. The test verifies visibility and animation goals/beginnings/active
  flags for every capture, including capture during a genuine animated move.
- Composition uses one custom element which returns native rectangle/texture
  elements at `RENDER_LAST_MOMENT`. Close removes queued custom elements, releases
  all capture textures/FBOs, and damages/schedules each output to erase the
  overlay. It must not restore an old damage ring on close and discard damage
  accumulated while the overview was open. Unload with an open overlay is tested.

**Validation and measurements.** Screenshot comparisons and the repeated
open/close test run in the existing disposable NixOS VM, whose plugin-free
parent reliably renders the nested child without a visible host window. The
host nested window is used only for development and a single hardware capture
benchmark; its parent may pause frame callbacks, so it is not the screenshot
or leak-test oracle. Both tests create their own second headless output, eight
distinct normal-workspace Foot fixtures (four per monitor), and one populated
special per monitor. Ordinary empty cells are captured too for the capacity test.

The VM captures 130 cells: two complete 8×8 grids plus two specials. At 160×90
RGBA8, each color attachment holds 57,600 bytes: **3.516 MiB per 8×8 monitor,
7.031 MiB for both grids, 7.141 MiB including the specials**. The code queries
actual GL texture dimensions/internal format and rejects a non-RGBA8 attachment
or an unexpected stencil attachment. No full-resolution per-cell framebuffer
is allocated. These are measured texture-storage dimensions and their exact
uncompressed payload, not a claim that driver allocation overhead is zero.

The separate AMD Radeon 780M / radeonsi hardware benchmark used 160×106 for the
resized Wayland monitor and 160×90 for the headless monitor: **7.776 MiB** of
color payload for all 130 cells. Allocation, CPU pass construction/submission
and GPU completion together took **23.38 ms total, 0.180 ms/cell mean,
0.096 ms median, 3.262 ms maximum**. The eight occupied normal cells had a
0.620 ms median; the two specials averaged 0.649 ms; empty cells had a 0.091 ms
median. Timings explicitly include a serialized `glFinish` after each cell;
they are end-to-end capture costs, not isolated GPU timer-query durations.
This fixture is much simpler than 128 occupied application workspaces.

AMD `/proc/PID/fdinfo` was sampled before allocation, while open, and after
close, deduplicated by DRM client ID when interpreting it. The main client's
resident VRAM changed from 9,792 to 15,928 KiB while GTT residency fell from
242,536 to 233,916 KiB. Driver BO migration/retirement and allocator caching
make that delta unsuitable as isolated per-texture resident memory. In
particular, driver memory need not fall immediately when GL objects are deleted.
Budget the verified color payload **plus driver/pool overhead**; do not label a
whole-process VRAM delta as the cache's exact footprint.

The VM checks the actual fixture colors in all ten occupied thumbnails and
compares full, unmasked screenshots on **both** outputs before/after close.
It repeats full allocation/capture/composition/close 25 times, checks all capture
texture/FBO names are gone using `glIsTexture`/`glIsFramebuffer`, bounds warmed
RSS variation, checks stable file-descriptor counts, and tests plugin unload
with the overlay open. The final llvmpipe VM run had a warmed mean of 22.81 ms per 130-cell batch
(0.120 ms median per cell); closed RSS stayed between 267,460 and 271,036 KiB
and descriptors stayed at 95. Both normal before/after comparisons and the
already-shown-special comparison changed zero pixels. `nix flake check
--builders '' -L` passed the plugin build, 16 Rust tests, formatting/Clippy
and the complete M1–M4-prototype VM suite. No unbounded retained resource
growth was observed.
Startup notifications and cursors are disabled/dismissed in the isolated
fixture so unrelated blinking UI cannot invalidate pixel comparisons.

**Recommended rendering design for the next step:** retain thumbnail-sized
textures only while open; capture populated visible cells/specials on open and
use a shared background for empty cells. Capture the first visible content
before showing the overlay, then budget further captures across compositor
frames to avoid a synchronous opening stall. Track per-cell dirty generations
from surface commits and window map/unmap/move/resize/workspace changes;
monitor damage alone misses hidden workspaces. Coalesce updates and recapture
only dirty cells displayed in the overview. Send frame callbacks to displayed
thumbnail clients as needed for animation, with a bounded refresh budget, and
stop doing work when closed or idle. Keep snapshot feedback suppression,
render-state guards and explicit close/unload cleanup. Production must not use
per-cell `glFinish`; rely on same-context ordering and appropriate compositor
synchronization instead.

No confirmed blocker remains for the tested GL capture/composition path.
Before calling the full overview production-ready, cover fractional scale,
rotated/HDR outputs, floating/fullscreen/pinned windows and popups, concurrent
screensharing, active transformer effects and monitor hotplug. Native transformer
or blur paths can allocate renderer scratch buffers separately from this color
cache; the prototype suppresses snapshot blur and does not establish a bound
for every effect. Vulkan support, damage-driven refresh, frame-callback policy,
physical monitor layout and input/focus behavior remain work for the full M4
implementation. Stop here until the user approves that work.

### M4 production overview

The approved path now has a Rust-owned layout and interaction model in
`core/src/ui.rs`. Panels follow the physical output bounding box, including
negative coordinates and vertical arrangements. Every output displays the same
combined overview, fitted to that output, so all grids remain accessible from
any monitor. Special workspaces have a labelled strip, dim empty cells and a
highlight for currently shown specials. Empty specials discovered while open
stay alive until close. Normal cell numbers appear on selection/hover/current
cells, avoiding a large burst of label rasterization on open.

Lua exposes `hl.plugin.hypr2d.overview()` as a callable constructor, consistent
with the other commands; README §Binds includes SUPER+TAB. Arrow/hjkl movement,
Tab/Shift-Tab panel/strip traversal, Enter, Esc and pointer activation are handled
by cancellable input listeners. Consumed key releases remain consumed even if
the overview closes between press and release; keys pressed before opening can

### Crash postmortem and bounded doctor recovery

The supplied live log ends after `ITarget: assignToSpace with a null space?`,
without a native backtrace. That warning alone is not proof of a pre-existing
null space: `CGroup::remove` deliberately clears a singleton member's ghost
before switching its window target back into the layout. The source and VM
establish the old swap's causal chain more precisely:

- `Actions::swapWith` → `CLayoutManager::switchTargets(..., true)` →
  `ITarget::swap` exchanges effective target spaces and calls `onUpdateSpace`.
- `CWindowGroupTarget::onUpdateSpace` visits member window targets using their
  old ghost spaces. It does **not** call `CGroup::updateWorkspace`, which is what
  synchronizes window workspaces and ghosts during normal `assignToSpace` moves.
- The grouped window stays in its old workspace while its effective target goes
  to the other workspace. If no window/monitor retains that other workspace, it
  expires: `ITarget::m_space` is a strong reference but `CSpace::m_parent` is weak.
  This is an orphan space (non-null space, null workspace), not necessarily a
  literal null `SP<CSpace>` before removal.
- Removing the singleton clears its member target normally, then swaps it with
  the orphan group target. Layout recalculation / window target space updates
  can dereference the expired workspace. The VM executes the removed old swap,
  asserts the orphan in doctor, and reproduces a crash using the public
  `out_of_group` dispatcher in a disposable compositor. This explains the live
  symptoms; the provided log cannot identify the live faulting instruction.

The saved VM crash report confirms SIGSEGV in
`CDwindleAlgorithm::calculateWorkspace`, reached through
`CAlgorithm::recalculate` → `ITarget::swap` → `CLayoutManager::switchTargets` →
`CGroup::remove` → `moveWindowOutOfGroupHelper` → the public Lua dispatcher.
Thus the reproduced singleton fails while recalculating the orphan layout,
before its final window-target space-update callback. Quarantining that orphan
algorithm before reinsertion is necessary; merely detaching the member first
